# コード変更と要求・設計整合プレレビュー計画 骨格

## 1. この計画で作るもの

コード変更が、要求書・基本設計書・詳細設計書・テスト仕様書と整合しているかを、正式レビュー前に bob がプレレビューできる仕組みを整備する。

ただし、bob は最終承認者ではない。bob は、根拠付きの指摘候補、確認質問、テスト不足候補、文書更新漏れ候補を提示する役割に限定する。

## 2. 目的

- 人間レビュー前に、変更内容と関連文書を整理する。
- 要求、設計、コード、テストの対応関係を見える化する。
- 不整合の疑いを早い段階で発見する。
- 人間がレビューで確認すべき観点を減らさず、探しやすくする。
- bob に不向きな最終判断や網羅保証をさせない運用にする。

## 3. 想定利用シーン

- 不具合修正後の設計追随確認
- 仕様追加後の要求・設計・コード・テスト整合確認
- 外部 I/F、共有メモリ、台帳変更を含む変更のプレレビュー
- 大きめの差分を正式レビューに出す前の観点整理
- 設計書更新漏れ、テスト観点漏れの洗い出し

## 4. 成果物の全体像

```text
docs/workflows/
  code-requirement-design-consistency-review.md
    詳細な運用フロー

.bob-review/
  review-package/
    bob 投入用の根拠パッケージ
  bob-output/
    bob の構造化レビュー結果
  human-triage/
    人間による採用・棄却・追加調査結果
  audit-log/
    実行条件、対象コミット、文書版数、プロンプト ID
```

## 5. レビュー対象の入力

### 5.1 必須入力

- 対象リポジトリ
- base commit / head commit
- 関連チケット ID
- 変更目的
- 変更種別
- 関連する要求書、設計書、テスト仕様書

### 5.2 任意入力

- 特に見てほしい観点
- 影響が大きいと想定しているモジュール
- 既知の懸念点
- 人間が事前に除外した対象
- 顧客確認済みの仕様判断

## 6. フローの大枠

```text
1. レビュー依頼を受け付ける
2. Git 差分を収集する
3. 変更されたコード要素を抽出する
4. 関連文書を抽出する
5. 要求・設計・コード・テストの対応候補を作る
6. 決定論的チェックを実行する
7. bob 投入用 review-package を作る
8. bob が整合プレレビューを行う
9. bob 出力を後処理する
10. 人間が採用・棄却・追加調査を判断する
11. 正式レビューへ引き継ぐ
```

## 7. 拡張機能で先に実施すること

AI に入れる前に、機械的に確定できる事実は拡張機能で処理する。

### 7.1 差分・コード解析

- 変更ファイル一覧の作成
- 変更関数一覧の作成
- 変更構造体、enum、define、typedef の抽出
- 呼び出し元・呼び出し先の候補抽出
- グローバル変数、共有メモリ、外部 I/F の参照抽出
- 変更行の周辺コンテキスト作成

### 7.2 文書解析

- Word / Excel / Markdown からのテキスト抽出
- 文書の版数、更新日、章番号、セクション ID の抽出
- 要求 ID、設計 ID、テスト ID の抽出
- 表の行・列構造を保った台帳情報の抽出
- 関連文書候補の検索

### 7.3 トレーサビリティ作成

- 要求 ID と基本設計 ID の対応
- 基本設計 ID と詳細設計 ID の対応
- 詳細設計 ID とコード要素の対応
- コード要素とテストケースの対応
- 対応なし、対応不明、候補のみの分類

### 7.4 決定論的チェック

- ビルド結果の取り込み
- 単体テスト結果の取り込み
- 静的解析結果の取り込み
- RT 処理内の禁止処理検出
- 外部 I/F、構造体サイズ、台帳更新漏れ候補の検出
- 文字コード、改行、不要差分の検出

## 8. bob に担当させること

bob は、入力された根拠を読み比べて、以下を行う。

- 要求とコードの不整合候補を出す。
- 設計とコードの不整合候補を出す。
- 要求外の副作用候補を出す。
- 異常系、境界値、状態遷移、組み合わせ条件の不足候補を出す。
- テスト観点の不足候補を出す。
- 文書・台帳更新漏れ候補を出す。
- 人間に確認すべき質問を作る。
- 正式レビューに引き継ぐための指摘文案を作る。

## 9. bob にさせないこと

bob には以下をさせない。

- マージ可否判断
- リリース可否判断
- 顧客要求を満たしているという最終承認
- 仕様の最終解釈
- ビルド・テスト成否の推測
- 影響範囲の完全網羅保証
- 外部 I/F 互換性の完全保証
- 性能、タイミング、安全性の合格判定
- 文書にない仕様の創作
- 根拠のない断定

## 10. bob 出力の基本形

bob の指摘は、次の形にそろえる。

```yaml
findings:
  - id: PRE-001
    category: design-code-consistency
    severity: high
    confidence: medium
    summary: "設計書の異常系処理と実装が一致していない可能性がある"
    evidence:
      - type: design
        ref: "DD-001 section 4.2"
      - type: code
        ref: "src/foo.c:120-170"
    reason: "設計ではエラー時に ERR_TIMEOUT を返すが、コードでは正常終了に合流しているように見える"
    recommended_action: "仕様判断を確認し、実装または詳細設計書を修正する"
    human_check: "この timeout 条件が今回変更対象に含まれるか確認する"
```

## 11. 実装フェーズ

### Phase 1: 最小構成

目的は、1 件の変更に対して bob 投入用パッケージを作れるようにすること。

- Git diff 収集
- 変更ファイル・変更関数の抽出
- 関連文書の手動指定
- 文書テキスト抽出
- review-package 生成
- bob 用プロンプト生成
- bob 出力保存

### Phase 2: 対応関係の自動化

目的は、要求・設計・コード・テストの対応候補を自動生成すること。

- 要求 ID / 設計 ID / テスト ID 抽出
- 台帳との照合
- 対応候補のスコア付け
- 未対応項目の抽出
- traceability-map 生成

### Phase 3: C/C++ 影響範囲解析

目的は、大規模 C/C++ 保守開発で重要な影響範囲を拾えるようにすること。

- 呼び出しグラフ作成
- グローバル変数アクセス解析
- 構造体変更影響解析
- 外部 I/F 変更影響解析
- RT / TS / 共有メモリ観点のルールチェック

### Phase 4: 運用統合

目的は、正式レビュー前の運用に組み込むこと。

- PR への結果添付
- Redmine / チケットとの関連付け
- 人間の採用・棄却結果保存
- 誤検知パターン蓄積
- 指摘傾向の集計

## 12. 最初の MVP 完了条件

- 対象コミット範囲を指定できる。
- 変更ファイル一覧を出力できる。
- 変更関数一覧を出力できる。
- 関連文書を手動指定できる。
- bob 投入用 review-package を生成できる。
- bob の結果を Markdown または YAML で保存できる。
- 人間が採用・棄却・追加調査を記録できる。
- bob が最終承認や網羅保証をしないよう制御できる。

## 14. 判断を分ける境界線

| 領域 | 担当 |
|---|---|
| diff、変更ファイル、変更関数の確定 | 拡張機能 |
| 文書 ID、表、版数、セクションの抽出 | 拡張機能 |
| ビルド、テスト、静的解析 | CI / 拡張機能 |
| 要求とコードの意味的なずれ候補 | bob |
| 設計と実装の矛盾候補 | bob |
| テスト観点不足候補 | bob |
| 仕様の最終解釈 | 人間 |
| 正式指摘にするかの判断 | 人間 |
| マージ・リリース可否 | 人間 |
