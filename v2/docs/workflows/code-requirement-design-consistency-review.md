# コード変更と要求書・設計書の整合プレレビューフロー

## 1. 目的

この文書は、コード変更が要求書・基本設計書・詳細設計書・テスト設計書と整合しているかを、人間の最終確認前に **bob がプレレビューするためのワークフロー**を定義する。

このフローの主眼は、bob に「最終判定」をさせることではなく、以下を人間のレビュー前に整理することである。

- 変更範囲と影響範囲を機械的に収集する。
- 要求・設計・コード・テストの対応関係を根拠つきで提示する。
- 不整合の疑い、設計更新漏れ、テスト観点不足、レビューで確認すべき問いを抽出する。
- bob が不得意な網羅性保証・最終承認・仕様解釈の決定を人間側に残す。

## 2. 位置付け

このフローは、正式レビューの前段に置く **プレレビュー**である。

```text
変更作成者
  ↓
拡張機能による前処理・根拠パッケージ作成
  ↓
bob による整合プレレビュー
  ↓
人間による確認・取捨選択・追加調査
  ↓
正式レビュー / 承認 / 差し戻し
```

bob の出力は、レビュー指摘候補・確認観点・根拠リンクの集合として扱う。承認可否、仕様の最終解釈、リスク受容は人間が決める。

## 3. 対象範囲

### 3.1 レビュー対象

- ソースコード変更
- ヘッダ・構造体・外部 I/F 定義の変更
- 設定ファイル、定数定義、テーブル定義の変更
- 要求書、基本設計書、詳細設計書、機能テスト仕様書の関連箇所
- 既存テスト、追加テスト、テストログ
- 変更理由が記載されたチケット、課題票、レビュー依頼文

### 3.2 対象外

- 人間の業務判断そのもの
- 顧客との合意事項の最終確定
- 安全性・品質保証上の承認
- 本番リリース可否判断
- 仕様書に書かれていない暗黙知の確定

## 4. 基本方針

1. **AI に入れる前に、事実はできるだけ拡張機能で確定する。**
   - diff、変更ファイル、関数一覧、呼び出し関係、要求 ID、設計 ID、テスト ID などは機械処理で抽出する。
2. **bob には、根拠を読んだうえでの整合性評価をさせる。**
   - 「この要求に対してコード変更が不足している可能性がある」など、根拠つきの仮説評価を担当させる。
3. **bob に網羅保証をさせない。**
   - 「全て確認済み」「問題なし」といった断定は禁止し、確認できた範囲を明示させる。
4. **人間が判断しやすい粒度で出力させる。**
   - 指摘、根拠、影響、確認手順、推奨アクションをセットで出す。
5. **レビュー結果は再現可能にする。**
   - bob に投入した根拠パッケージ、プロンプト、出力、対象コミットを保存する。

## 5. 全体フロー

### Step 0: レビュー依頼の受付

変更作成者は、レビュー依頼時に以下を指定する。

- 対象ブランチまたはコミット範囲
- 関連チケット ID
- 関連要求書・設計書・テスト仕様書
- 変更目的
- 変更種別
  - 不具合修正
  - 仕様追加
  - 仕様変更
  - リファクタリング
  - 性能改善
  - 保守性改善
- 人間レビューで特に見てほしい観点

### Step 1: コード変更の収集

拡張機能で以下を収集する。

- 変更ファイル一覧
- 追加・変更・削除された関数
- 変更された構造体、enum、define、typedef
- 変更された外部 I/F、ファイル I/O、通信 I/F
- 変更されたグローバル変数、共有メモリ、状態変数
- 変更行の周辺コンテキスト
- 変更前後の関数シグネチャ
- 変更前後の呼び出し関係
- 変更前後のデータ参照・更新箇所

この段階の出力は bob の解釈に頼らず、機械処理結果として保存する。

### Step 2: 関連ドキュメントの抽出

拡張機能で以下を抽出する。

- 関連チケットの本文、受入条件、補足コメント
- 要求書の該当セクション
- 基本設計書の該当セクション
- 詳細設計書の該当セクション
- 機能テスト仕様書の該当ケース
- I/F 台帳、メッセージ台帳、エラーコード台帳、ファイル仕様台帳の該当行

抽出時は、文書名・版数・更新日時・セクション ID・表番号・行番号を保持する。

### Step 3: トレーサビリティ候補の作成

拡張機能で、要求・設計・コード・テストの対応候補を作る。

```text
要求 ID
  └─ 基本設計 ID
      └─ 詳細設計 ID
          ├─ 関連ファイル / 関数 / 構造体
          └─ 関連テストケース
```

対応付けの根拠は、以下を優先する。

1. 明示 ID
2. ファイル名、関数名、構造体名、I/F 名
3. メッセージ ID、エラー ID、パラメータ ID
4. 既存の対応表・台帳
5. 近傍コメント、節タイトル、キーワード一致
6. bob による補助的な類似判断

1〜5 は拡張機能で処理し、6 は補助情報として扱う。bob の類似判断だけで対応関係を確定しない。

### Step 4: 影響範囲の機械分析

拡張機能で、変更箇所から影響範囲を広げる。

- 直接変更された関数
- 呼び出し元、呼び出し先
- 参照・更新されるグローバル変数
- 変更された構造体を利用する関数
- 外部 I/F の利用箇所
- 状態遷移、モード遷移、異常系処理
- RT スレッド、TS サービス、共有メモリ、I/O 処理への波及
- テストケースの既存カバレッジ

影響範囲は「確定」「候補」「不明」に分類する。

### Step 5: 決定論的チェック

AI に投げる前に、拡張機能または CI で以下を確認する。

- ビルド可否
- 単体テスト結果
- 静的解析結果
- 文字コード、改行、不要差分
- 禁止 API の使用
- RT 処理内の I/O、動的確保、ブロッキング処理の混入
- 共有メモリ構造体のサイズ・アラインメント変化
- 外部 I/F、ファイル形式、メッセージ形式の破壊的変更
- 台帳更新漏れ候補
- テスト仕様書更新漏れ候補

ここで判定できるものは、bob に「推測」させない。

### Step 6: bob 投入用パッケージの作成

拡張機能は、bob に投入する入力を次の構成で作る。

```text
review-package/
  manifest.yaml
  change-summary.md
  diff-context.md
  traceability-map.md
  deterministic-checks.md
  requirements.md
  basic-design.md
  detailed-design.md
  test-spec.md
  code-slices/
  tables/
  prompts/
```

#### manifest.yaml

- 対象リポジトリ
- 対象ブランチ
- base commit
- head commit
- 変更者
- 作成日時
- 関連チケット
- 関連文書
- 実行した前処理バージョン
- bob に投入したプロンプト ID

#### change-summary.md

- 変更目的
- 変更種別
- 変更ファイル一覧
- 変更関数一覧
- 影響範囲サマリ

#### traceability-map.md

- 要求 ID と設計 ID の対応
- 設計 ID とコードの対応
- コードとテストケースの対応
- 対応根拠
- 未対応・不明箇所

#### deterministic-checks.md

- ビルド結果
- テスト結果
- 静的解析結果
- 台帳チェック結果
- 禁止ルールチェック結果

### Step 7: bob による整合プレレビュー

bob には、以下の観点でレビューさせる。

#### 7.1 要求とコード変更の整合

- 要求に対して実装変更が不足していないか
- 要求外の動作変更が混入していないか
- 要求の例外条件、異常系、境界値が実装されているか
- 要求にない仕様判断がコード内で行われていないか

#### 7.2 基本設計とコード変更の整合

- 処理方式、責務分担、データ流れが基本設計と矛盾していないか
- 状態遷移、モード遷移、I/O タイミングが設計と合っているか
- RT / TS の役割分担に反していないか
- 既存アーキテクチャ上、不自然な依存が増えていないか

#### 7.3 詳細設計とコード変更の整合

- 条件分岐、戻り値、エラー処理が詳細設計と合っているか
- パラメータ範囲、単位、丸め、符号、初期値が合っているか
- 構造体メンバ、テーブル、定数の使い方が合っているか
- 詳細設計書にない処理が追加されていないか

#### 7.4 テスト仕様との整合

- 変更内容に対して既存テストが足りるか
- 新規テストケースが必要か
- 異常系、境界値、状態遷移、組み合わせ条件が不足していないか
- 要求・設計に対するテストの対応が切れていないか

#### 7.5 ドキュメント更新漏れ

- コード変更に対して要求書・設計書・台帳の更新が必要か
- 設計書だけ変わってコードが変わっていない箇所がないか
- コードだけ変わって設計が追随していない箇所がないか
- 用語、ID、表現の不一致がないか

### Step 8: bob 出力の後処理

拡張機能で bob の出力を整形する。

- 指摘の重複統合
- 根拠リンクの検証
- 存在しないファイル・行番号・ID の除去
- severity の暫定分類
- 人間確認が必要な項目の抽出
- 機械的に確認済みの項目との照合

bob 出力は、以下の形式に整える。

```yaml
findings:
  - id: PRE-001
    category: requirement-code-consistency
    severity: high
    confidence: medium
    summary: "要求 REQ-123 の異常系条件に対する実装が不足している可能性がある"
    evidence:
      - type: requirement
        ref: "REQ-123"
      - type: code
        ref: "src/control/foo.c:120-168"
      - type: design
        ref: "詳細設計 DD-45"
    reason: "要求では timeout 時に ERR_TIMEOUT を返すが、変更後コードでは timeout 分岐が正常終了に合流しているように見える"
    recommended_action: "timeout 分岐の期待動作を確認し、実装または詳細設計を修正する"
    human_check: "REQ-123 の timeout 条件が今回変更対象かを確認する"
```

### Step 9: 人間によるプレレビュー結果の確認

人間は、bob の指摘を以下に分類する。

- 正式レビューで指摘する
- 作成者に事前確認する
- 追加調査する
- 誤検知として閉じる
- 今回対象外として記録する

この段階で、bob の指摘をそのまま正式指摘にしない。人間が根拠を確認し、必要に応じて文言を修正する。

### Step 10: 正式レビューへの引き継ぎ

正式レビューには以下を渡す。

- 変更サマリ
- トレーサビリティ表
- 決定論的チェック結果
- bob プレレビュー結果
- 人間が採用した指摘
- 人間が棄却した指摘と理由
- 未解決の確認事項

## 6. AI 投入前に拡張機能で実施すべき前処理

### 6.1 Git / 差分収集

| 処理 | AI に任せない理由 | 出力 |
|---|---|---|
| base/head の確定 | レビュー対象を誤ると全結果が崩れる | 対象コミット |
| 変更ファイル一覧 | 機械的に確定できる | changed-files.json |
| diff 抽出 | 正確性が必要 | diff-context.md |
| rename / delete 検出 | AI では取りこぼしやすい | file-status.json |
| 変更行の関数所属判定 | 根拠位置が必要 | changed-symbols.json |

### 6.2 コード構造解析

| 処理 | AI に任せない理由 | 出力 |
|---|---|---|
| 関数定義・宣言抽出 | 正確な索引が必要 | functions.json |
| 呼び出し関係抽出 | 影響範囲の土台 | call-graph.json |
| グローバル変数参照抽出 | C コードでは重要 | data-access.json |
| 構造体・enum・define 抽出 | I/F 破壊検知に必要 | symbols.json |
| RT 禁止処理検出 | ルールベースで判定すべき | rule-violations.json |

### 6.3 文書抽出

| 処理 | AI に任せない理由 | 出力 |
|---|---|---|
| Word / Excel / Markdown からのテキスト抽出 | 入力欠落を避ける | document-chunks.json |
| セクション ID 抽出 | 根拠追跡に必要 | section-index.json |
| 表の行・列保持 | 台帳照合に必要 | table-index.json |
| 版数・更新日抽出 | 古い文書を避ける | document-metadata.json |
| 要求 ID / 設計 ID / テスト ID 抽出 | 対応表の土台 | artifact-ids.json |

### 6.4 トレーサビリティ作成

| 処理 | AI に任せない理由 | 出力 |
|---|---|---|
| 明示 ID による対応付け | 機械的に確定可能 | trace-map.json |
| 台帳による対応付け | 機械的に確定可能 | ledger-links.json |
| ファイル名・関数名による対応候補 | 再現性が必要 | candidate-links.json |
| 対応なし項目の検出 | レビュー観点の入口 | unmapped-items.json |
| 類似度候補の作成 | bob の入力を狭める | similarity-candidates.json |

### 6.5 チェック結果の収集

| 処理 | AI に任せない理由 | 出力 |
|---|---|---|
| ビルド実行 | 事実確認 | build-result.json |
| 単体テスト実行 | 事実確認 | test-result.json |
| 静的解析 | ルール判定 | static-analysis.json |
| 台帳更新漏れチェック | 差分照合で可能 | ledger-check.json |
| 文字コード・改行チェック | ルール判定 | format-check.json |

### 6.6 bob 入力制御

| 処理 | AI に任せない理由 | 出力 |
|---|---|---|
| 入力トークン量の制御 | 欠落や切り捨てを防ぐ | package-manifest.yaml |
| 根拠の優先順位付け | 重要箇所を落とさない | evidence-priority.json |
| 機密・不要情報の除外 | 安全な入力管理 | redaction-report.json |
| プロンプト ID の付与 | 再現性確保 | prompt-manifest.yaml |

## 7. bob に担当させる項目

bob に向いているのは、複数の根拠を読み比べたうえで「矛盾の疑い」や「人間が確認すべき論点」を出す作業である。

- 要求と実装の意味的なずれの候補抽出
- 設計書とコード構造の不自然な差分抽出
- 例外条件、境界条件、異常系の不足候補抽出
- テスト観点の不足候補抽出
- ドキュメント更新漏れ候補抽出
- レビュー観点の整理
- 指摘文の下書き
- 人間に確認すべき質問の生成
- 変更目的に対する影響リスクの説明

## 8. bob にさせるべきではない項目

### 8.1 最終判断

bob に以下を判断させない。

- マージ可否
- リリース可否
- 顧客要求を満たしているという最終承認
- 安全性・品質保証上の合格判定
- 不具合流出リスクの受容可否

### 8.2 事実の確定

bob に以下を事実として確定させない。

- ビルドが通るか
- テストが通るか
- すべての影響範囲を洗い出したか
- すべての要求を網羅したか
- 台帳が完全に更新されているか
- 外部 I/F 互換性が完全に保たれているか

これらは拡張機能、CI、静的解析、人間確認で扱う。

### 8.3 文書にない仕様の決定

bob に以下を決めさせない。

- 曖昧な要求の最終解釈
- 顧客確認が必要な仕様判断
- 既存仕様と新仕様が衝突した場合の優先順位
- 仕様書にない暗黙ルールの採否
- 例外処理の業務上の正解

### 8.4 高精度な数値・網羅確認

bob に以下を主担当させない。

- 大量表の完全一致確認
- バイナリ互換性の保証
- 構造体サイズ・アラインメントの保証
- 全ファイル全関数の網羅的な呼び出し解析
- 性能劣化の定量判定
- タイミング制約の保証

### 8.5 根拠なしの指摘

bob に、根拠ファイル・根拠 ID・根拠行がない指摘を出させない。根拠が弱い場合は「確認質問」として扱う。

## 9. bob 用プロンプトの基本ルール

bob に投入するプロンプトには、最低限以下を含める。

```text
あなたは正式レビュー前のプレレビュー担当である。
最終承認、マージ可否、仕様の最終決定はしない。
入力された根拠だけを使用し、根拠がない推測は「確認質問」として出す。
「問題なし」「全て確認済み」と断定しない。
指摘には、必ず根拠、理由、影響、推奨アクション、人間確認事項を含める。
```

### 9.1 bob への禁止指示

```text
禁止事項:
- 根拠のない断定をしない。
- 入力にない仕様を作らない。
- すべて網羅したと主張しない。
- ビルドやテストの成否を推測しない。
- 人間の承認判断を代替しない。
- 指摘を水増ししない。
```

### 9.2 bob の出力分類

bob の指摘は、以下のカテゴリに分類する。

| カテゴリ | 内容 |
|---|---|
| requirement-code-consistency | 要求とコードの不整合候補 |
| design-code-consistency | 設計とコードの不整合候補 |
| test-gap | テスト観点不足候補 |
| document-update-gap | 文書・台帳更新漏れ候補 |
| unintended-change | 要求外変更候補 |
| risk | 影響リスク |
| question | 人間への確認質問 |

### 9.3 severity の目安

| severity | 目安 |
|---|---|
| critical | 安全性、外部 I/F 破壊、本番障害、要求未達につながる可能性が高い |
| high | 要求・設計との明確な不整合、異常系欠落、テスト不足が強く疑われる |
| medium | 仕様解釈、設計追随、影響範囲の確認が必要 |
| low | 表記ゆれ、軽微な文書追随、改善提案 |
| info | レビュー補助情報、確認メモ |

confidence は high / medium / low で別管理する。severity と confidence を混同しない。

## 10. 拡張機能の実装計画

### Phase 1: MVP

目的は、bob に安全に投入できる最小パッケージを作ること。

- Git diff 収集
- 変更ファイル・変更関数の抽出
- 関連文書の手動指定
- Word / Excel / Markdown のテキスト抽出
- 要求 ID / 設計 ID / テスト ID の抽出
- review-package の生成
- bob 用プロンプト生成
- bob 出力の YAML/Markdown 保存

### Phase 2: トレーサビリティ強化

- 要求・設計・コード・テストの対応表生成
- 台帳との自動照合
- 未対応項目の抽出
- 類似度による候補提示
- 対応根拠の強度スコア付け

### Phase 3: C/C++ 影響範囲解析

- 関数呼び出しグラフ生成

## 12. 人間レビューで必ず確認する項目

bob プレレビュー後、人間は以下を必ず確認する。

- bob が参照した要求書・設計書が正しい版か
- 関連文書の抽出漏れがないか
- bob 指摘の根拠が実在するか
- 指摘が今回変更範囲に対して妥当か
- 指摘を正式レビューに出すべきか
- 誤検知の場合、なぜ誤検知か
- 仕様判断が必要な場合、誰に確認するか
- テスト追加が必要な場合、どの工程で対応するか

## 13. 運用上の注意

- bob の指摘件数を品質指標として直接使わない。
- bob の「指摘なし」を正式な合格判定にしない。
- 入力文書が古い場合、bob の出力も古い前提に引きずられる。
- 暗黙知が多い領域では、bob の出力より確認質問を重視する。
- 重要度の高い制御、I/F、共有メモリ、RT 処理は人間確認を必須にする。
- 誤検知は残しておき、後続の前処理・プロンプト改善に使う。

## 15. 完了条件

このワークフローの初期版は、以下を満たしたら完了とする。

- 1 件のコード変更に対して review-package を生成できる。
