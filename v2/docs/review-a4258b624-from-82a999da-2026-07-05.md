## REV-A4258-01: approval guardrail の内部 state namespace が外部 `stateUpdates` から書ける

### Severity

High

### 対象

- `extensions/workflow-register/src/extension.ts`
- `extensions/workflow-register/src/workflowRegisterService.ts`
- `extensions/workflow-register/src/bobStepRuntime.ts`
- `extensions/workflow-register/src/core/approvalGuardrails.ts`

### 観察

`workflowRegister.completeStep` は VS Code command として公開されており、`StepCompletionOptions` を受け取って `service.completeCurrentStep(options)` に渡す。

`WorkflowRegisterService.completeCurrentStep()` は `stateUpdates` を `StepRuntime.completeCurrentStep()` へ渡す。

`StepRuntime` 側の `applyStateUpdates()` は、渡された key / value をほぼそのまま active workflow state に書き込む。

一方で、approval guardrail は `workflow.approval.<stepId>` という state key を内部状態として使う。そこに `status: "approved"` と一致する fingerprint が入っていると、承認済みとして扱う。

### 問題

外部から渡される `stateUpdates` と、engine 内部の approval state が同じ `run.state` namespace を共有している。

そのため、悪意ある companion extension、想定外の GUI action、または将来追加される completion 経路が `workflow.approval.<stepId>` を直接書き換えると、approval guardrail の安全境界を迂回できる可能性がある。

現状は trusted workspace 前提であり、直ちに外部攻撃へ直結するとは限らない。ただし、approval guardrail は安全機能であるため、内部 state namespace を外部入力から保護する必要がある。

### 影響

- command approval guardrail の承認状態が外部 state update により偽装される可能性がある。
- `workflow.review.*`、`workflow.branching.*` など他の内部制御 state も同じリスクを持つ。
- 将来の workflow / GUI / companion extension 拡張で、意図せず内部 state を破壊する可能性がある。

### 推奨対応

最低限、以下の prefix を予約 key として扱い、外部入力由来の `stateUpdates`、workflow `resultKey`、manual `form.resultKey`、manual `approval.resultKey` から拒否する。

```text
workflow.
workflow.approval.
workflow.review.
workflow.branching.
```

より堅くするなら、engine 内部 state を `run.internal` のような別領域に分離し、workflow-visible state と混ぜない構造にする。

最小修正例:

```ts
function assertUserStateKey(key: string): void {
  if (key === "workflow" || key.startsWith("workflow.")) {
    throw new Error(`Reserved workflow state key cannot be written by workflow/user updates: ${key}`)
  }
}
```

適用候補:

- `applyStateUpdates()`
- `applyManualCompletionState()`
- workflow parser / validator の `resultKey` 系検証
- authoring / GUI builder の resultKey validation

### 追加したいテスト

```ts
test("workflowRegister.completeStep rejects reserved workflow state updates", async () => {
  // stateUpdates: { "workflow.approval.collect": "..." } を渡した場合に拒否されること
})
```

```ts
test("workflow validator rejects reserved resultKey prefixes", () => {
  // resultKey: "workflow.approval.collect" を含む workflow を invalid にすること
})
```

## REV-A4258-02: `extensions-quality.yml` の path filter が実行 scripts を一部監視していない

### Severity

Medium

### 対象

- `.github/workflows/extensions-quality.yml`
- `scripts/check-import-cycles.js`
- `scripts/check-vsix-policy.js`
- `scripts/run-unused-checks.js`

### 観察

新規追加された `extensions-quality.yml` は、各拡張で次のような品質チェックを実行する。

- `npm ci`
- dependency policy
- architecture policy
- source policy
- unused dependency report
- production dependency audit
- unit tests
- package
- VSIX policy

一方で、workflow trigger の `paths` には一部 script だけが含まれている。

現在含まれている script:

```yaml
- "scripts/check-artifact-size-policy.js"
- "scripts/check-export-star-policy.js"
- "scripts/report-extension-metrics.js"
```

しかし、各 extension の package script では次の script も実行される。

```json
"architecture:policy": "node ../../scripts/check-import-cycles.js src",
"unused:report": "node ../../scripts/run-unused-checks.js",
"package:policy": "node ../../scripts/check-vsix-policy.js --max-bytes 200000"
```

### 問題

`check-import-cycles.js`、`run-unused-checks.js`、`check-vsix-policy.js` だけを変更した PR / push では、`extensions-quality` workflow が起動しない可能性がある。

品質ゲートのスクリプト自体を変更しても品質ゲートが走らないため、CI の自己防衛として弱い。

### 影響

- import cycle policy の破損を CI で検出できない可能性がある。
- VSIX policy の破損を CI で検出できない可能性がある。
- unused report script の変更が CI で検証されない可能性がある。
- 品質 gate 変更 PR のレビュー漏れにつながる。

### 推奨対応

`pull_request.paths` と `push.paths` の両方に、少なくとも以下を追加する。

```yaml
- "scripts/check-import-cycles.js"
- "scripts/check-vsix-policy.js"
- "scripts/run-unused-checks.js"
```

より単純には、以下へ寄せる。

```yaml
- "scripts/*.js"
```

この方が今後 script が増えた場合にも漏れにくい。

### 追加したい確認

- `scripts/*.js` のみを変更した PR で `extensions-quality` が起動すること。
- `check-import-cycles.js`、`check-vsix-policy.js`、`run-unused-checks.js` の変更で workflow が起動すること。

## 5. 補足確認

### 5.1 path / VCS 境界

`bob-code-consistency-review` では、`review-input.yaml` 自体と artifact path が strict resolver で workspace 内に限定されるようになっている。

Git revision は `rev-parse --verify --end-of-options` で commit SHA 化される。

Bazaar revision は、長さ、先頭 `-`、`..`、許可文字種を検証してから `bzr --no-aliases diff -r <base>..<head>` に渡される。

この領域は、今回レビュー範囲では大きな追加指摘なし。

### 5.2 MCP allowed roots

`bob-bazaar-review` の MCP server は `BOB_BAZAAR_ALLOWED_ROOTS` を参照し、cwd が allowed root 配下かを `realpath` と `path.relative` で判定している。

allowed root 外を拒否し、allowed root 配下を許可するテストも追加されている。

この領域も方向性は良い。

### 5.3 review packet の repositoryRoot 引き継ぎ

Bazaar GUI で review packet を作成した際、`repositoryRoot` を workflow state に保存し、後続の `collectReviewContext()` で explicit workspace path として使う構成になっている。

これにより、packet 本文側で local path を redaction した場合でも、workflow context に repository root を渡せる。

設計意図として妥当。ただし、`workflow state` に内部制御情報を置く設計であるため、REV-A4258-01 の予約 key 保護をセットで入れるのが望ましい。
